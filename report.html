KS001Execution control

Retry loop

What it is: A retry loop occurs when a materially identical goal is attempted again without new evidence, a changed workspace state, or a different execution strategy.

Detection evidence: 105 sessions (48.8%) belong to 7 repeated actionable-prompt groups.

Why it matters: Repeated requests are not automatically waste, but they are a strong signal that retries can proceed without new evidence or a changed execution path.

Recommended optimization: Before retrying a goal, require a changed failure signature, a workspace change, or explicit approval.

Signal→Risk→Intervention→Verification→Metric

Implementation backlog

skill retry-admission-gate

Build:

  1. Define a retry card: prior attempt, observed blocker, what changed, and next verification command.
  2. Require the card before an agent resumes a materially identical goal.

Verify: Run three known retry cases; the gate must reject an unchanged retry and allow a retry with recorded new evidence.

Measure: Repeated-prompt session share

harness retry-dedup hook

Build:

  1. Fingerprint the normalized task request at session start.
  2. When the fingerprint recurs within a chosen window, surface the prior outcome and require a change reason.

Verify: Track gate decisions and confirm that every admitted repeat has a recorded change reason.

Measure: Admitted repeats without a change reason

KS002Context management

Context sprawl

What it is: Context sprawl occurs when one session keeps accumulating turns after its goal, repository, or work mode has changed, instead of starting a bounded follow-up session.

Detection evidence: 21 sessions (9.8%) reached 15 or more turns.

Why it matters: Long sessions can be productive; the practical risk is carrying obsolete assumptions and tool state after the work has changed phase.

Recommended optimization: After a goal-family or work-mode change, start a new session with a short handoff: outcome, non-goals, evidence, and next stop condition.

Signal→Risk→Intervention→Verification→Metric

Implementation backlog

technique phase-boundary handoff

Build:

  1. Use a five-field handoff: achieved outcome, active decision, non-goals, verification state, next stop condition.
  2. Start a fresh worker session whenever the goal, repository, or execution mode changes.

Verify: Review ten handoffs: every field must be present and the next worker must be able to run the named verification without reading the previous transcript.

Measure: Turns after last phase change

harness turn-budget checkpoint

Build:

  1. At a configurable turn threshold, ask whether the current goal and repository are unchanged.
  2. If not, emit the handoff template and end the worker session.

Verify: Simulate a repository change and confirm the checkpoint creates a handoff instead of extending the old context.

Measure: Sessions exceeding turn budget without a handoff

KS003Context management

Context churn

What it is: Context churn occurs when repeated context compaction forces an agent to reconstruct decisions, constraints, or verification state that should have been carried forward explicitly.

Detection evidence: 21 sessions (9.8%) have multiple or dense compactions.

Why it matters: Compaction is a normal context-management mechanism. The improvement opportunity is preserving decision-critical state so the resumed agent does not rediscover it.

Recommended optimization: Keep summaries structured around active outcome, decisions, non-goals, verification state, and blockers; do not treat compaction count alone as a failure.

Signal→Risk→Intervention→Verification→Metric

Implementation backlog

skill context-resume-contract

Build:

  1. Add a compact-before-resume template with the five decision-critical fields.
  2. Require a named source of truth for any unresolved decision or verification claim.

Verify: Give a fresh agent only the compacted handoff and confirm it can identify the next action, constraint, and verification command.

Measure: Post-compaction rediscovery turns

harness compaction quality check

Build:

  1. Detect compaction events and attach a structured checklist to the next turn.
  2. Flag missing outcome, blocker, or verification state for human review.

Verify: Sample compacted sessions and score the checklist completion rate.

Measure: Complete compaction handoffs

KS005Execution control

Tool-loop hotspot

What it is: A tool-loop hotspot occurs when a session makes unusually many tool calls without a visible decision, changed hypothesis, or completed verification step between batches.

Detection evidence: 20 sessions (9.3%) issued 327 or more tool calls; the threshold is three times the session average.

Why it matters: High tool volume can be legitimate for broad work. It becomes a smell when repeated inspection or failed actions replace a bounded verification loop.

Recommended optimization: Introduce an explicit tool budget and require a decision or verification checkpoint before extending it.

Signal→Risk→Intervention→Verification→Metric

Implementation backlog

technique tool-budget loop

Build:

  1. State the next evidence needed before invoking a tool.
  2. After a small batch of calls, decide: verify, change approach, or stop for input.

Verify: Review hotspot sessions and confirm each tool batch ends in an explicit decision rather than another unbounded search.

Measure: Tool calls per verified outcome

harness tool-loop checkpoint

Build:

  1. Count tool calls per goal phase.
  2. At the configured budget, prompt for the expected evidence and current hypothesis before continuing.

Verify: Use a fixture with repeated failed calls; verify that the checkpoint asks for a hypothesis rather than silently permitting another batch.

Measure: Tool-call budget overruns
